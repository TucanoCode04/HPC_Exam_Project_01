\subsection{Implementation notes}
\begin{itemize}
\item 3 MPI ranks = 3 independent scenarios (task parallelism, no inter-rank communication except a final \texttt{MPI\_Allreduce} on success/failure). No domain decomposition.
\item Each rank: OpenMP-parallel stencil update (\texttt{compute\_next}, same 5-point Laplacian as parts 1--2) + CUDA colorization/PPM write per frame.
\item CUDA: \texttt{colorize\_kernel}, one GPU thread per pixel. Normalize by fixed scale 58 $\to$ $\sqrt{|\cdot|}$ contrast boost $\to$ fade white$\to$red/orange (positive) or white$\to$blue (negative) past \texttt{zero\_band}.
\item Colorizer context (device buffers, pinned host RGB buffer) allocated once per scenario, reused across all frames -- not re-allocated per frame.
\item Host RGB buffer uses \texttt{cudaHostAlloc} (pinned), not \texttt{malloc} -- faster DMA transfer.
\item ASCII PPM writer: one pre-sized buffer, hand-rolled byte$\to$ASCII digit conversion, single \texttt{fwrite} per frame -- replaced an earlier per-pixel \texttt{fprintf} approach (suspected main CPU-side cost, same class of bottleneck as \texttt{fwrite} in part 1's VTune hotspots).
\item No Makefile. Build = 3 commands: \texttt{mpicc} compiles/links the C+MPI+OpenMP side (knows its own MPI paths automatically); \texttt{nvcc} compiles only \texttt{wave\_color\_cuda.cu}; \texttt{mpicc} links both objects, given \texttt{-L\$CUDA\_HOME/lib64 -lcudart -lstdc++}.
\item CLI trimmed to just \texttt{--size}, \texttt{--steps}, \texttt{--threads}, \texttt{--block-size} -- physical parameters and amplitudes are fixed \texttt{\#define}s, not runtime flags, since they're never actually varied.
\item \texttt{assignment\_3.c} accepts exactly 1 MPI rank as an explicit "solo" benchmark mode (runs sim1 alone with exclusive GPU access), in addition to the normal $\geq 3$-rank production mode. Added specifically to measure GPU contention (see below).
\end{itemize}

\subsection{Physical execution model on \texttt{edu\_a40} nodes}
\begin{itemize}
\item Node hardware: 2$\times$ Intel Xeon 6442Y (24 physical cores each, SMT $\to$ 48 logical/socket, 96/node), 4$\times$ A40 GPU, all sharing one motherboard's PCIe/memory. \texttt{--nodes=1} $\Rightarrow$ all 3 ranks always land on one physical node.
\item MPI here is \emph{not} doing cross-node distribution -- Infiniband is idle for this workload. 3 ranks = 3 separate OS processes (separate address spaces) on the same machine; the only real message sent is the final \texttt{MPI\_Allreduce}. Everything else is 3 fully independent executions sharing hardware.
\item OpenMP: \texttt{\#pragma omp parallel for} forks a thread team at that line, joins at the implicit barrier -- fresh fork/join on every one of the 300 \texttt{compute\_next} calls per rank. \texttt{OMP\_PROC\_BIND=close}/\texttt{OMP\_PLACES=cores} pins threads to specific logical cores, clustered rather than scattered -- matters because this is a dual-socket NUMA machine (2 separate memory controllers; cross-socket = "remote" access, slower than local).
\item Likely (not yet confirmed via \texttt{numastat}) NUMA behavior: \texttt{calloc}'d pages are lazily backed by Linux (no physical page until first write), and the first real write to most pages happens inside \texttt{compute\_next}'s OpenMP loop. Since \texttt{schedule(static)} gives the same thread the same row range on every call, first-touch naturally lands each page's physical memory on whichever socket that thread runs on, and stays consistent run to run -- similar effect to part 1's explicit parallel-initialization NUMA fix, achieved here as a side effect of \texttt{static} + \texttt{calloc}.
\item CUDA: \texttt{--gres=gpu:1} $\Rightarrow$ all 3 ranks share the \emph{same} one of the node's 4 physical A40s (not one each). Each rank opens its own CUDA context on that one GPU; the NVIDIA driver time-slices the SMs across the 3 contexts' kernel launches (default sharing mode, not MPS spatial partitioning -- no dedicated slice per rank). The PCIe link to that GPU is likewise shared for all 3 ranks' H2D/D2H copies. This is exactly what the solo-vs-shared contention sweep is measuring.
\end{itemize}

\subsection{OpenMP schedule policy -- static vs. dynamic/guided}
\begin{itemize}
\item Current choice: \texttt{schedule(static)} for both the stencil loop and the boundary-zeroing loop.
\item Reasoning against switching: the stencil is a dense, regular grid -- every interior point does identical work, so there is no load imbalance for \texttt{dynamic}/\texttt{guided} to correct. Both would add real per-chunk dispatch overhead for zero balancing benefit.
\item Bigger reason: \texttt{dynamic}/\texttt{guided} hand out chunks based on runtime timing, so which thread touches which rows can vary between calls to \texttt{compute\_next} -- this breaks the consistent thread-to-row mapping the first-touch NUMA argument above depends on, and would cost repeated cache/NUMA-locality loss on every single call (300 times per rank).
\item Corroborating precedent: part 1's own report (Section~\ref{sec:testing}) found exactly this -- switching \texttt{guided}$\to$\texttt{static} for the compute-only (no I/O) case improved efficiency at every thread count tested (e.g. 45.4\% vs 27.0\% at $P=64$), attributed to preserved NUMA locality.
\item Also: \texttt{compute\_next} is $\sim$2\% of total wall-clock time (Section on size sweep) -- even a real scheduling-policy win there would be nearly invisible in total run time, since GPU colorize+write dominates so completely.
\item Decision: not running a schedule-policy sweep. The a priori reasoning + part 1's own measured precedent both point the same direction, and an empirical confirmation was considered and deliberately skipped -- not worth the run time for a result this predictable.
\end{itemize}

\subsection{Unexplored infrastructure/design options}
\begin{itemize}
\item \textbf{Multi-node MPI (\texttt{--nodes=3}, 1 rank/node).} Currently unused: \texttt{--nodes=1} means MPI's cross-node capability (Infiniband) sits idle, only the final \texttt{Allreduce} is real traffic. Since the 3 scenarios are fully independent, \texttt{--nodes=3} is possible. Bonus: \texttt{--gres=gpu:1} is per-node, so this would also give each rank a fully dedicated GPU -- eliminates CPU-core contention (no more 96-way split) and GPU contention simultaneously. Cost: asks for 3 whole nodes + 3 whole A40s at once instead of 1+1 -- reasonable as a one-off comparison experiment, not as the new default for repeated sweep runs on a shared 4-node partition. \textbf{Status: \texttt{contention\_multinode.sh} added} (\texttt{--nodes=3 --ntasks-per-node=1 --gres=gpu:1}), appends a \texttt{multinode} mode to \texttt{contention\_sweep.csv}; not yet run.
\item \textbf{Clarification: \texttt{--gres} is per-node, not per-job.} Question raised: why not one script with \texttt{--nodes=3} \emph{and} \texttt{--gres=gpu:3}, to get "3 nodes and 3 GPUs"? Answer: \texttt{--gres=gpu:N} already specifies GPUs \emph{per node}, so \texttt{--nodes=3 --gres=gpu:1} (what \texttt{contention\_multinode.sh} already uses) means 1 GPU/node $\times$ 3 nodes = 3 GPUs total, one per rank -- exactly "3 nodes and 3 GPUs" already. Writing \texttt{--gres=gpu:3} together with \texttt{--nodes=3} would instead request 3 GPUs \emph{per node} $\times$ 3 nodes = 9 GPUs total; since \texttt{cuda\_colorizer\_select\_device} only ever puts one rank on one GPU, the other 6 would sit reserved and unused -- a much larger, harder-to-schedule request for no benefit. No new script needed; \texttt{contention\_multinode.sh} already implements the intended setup.
\item \textbf{Why \texttt{distributed} and \texttt{multinode} are separate scripts, not one.} \texttt{--nodes} is a job-wide SLURM resource fixed at submission time (unlike \texttt{--size}/\texttt{--threads}, which are just program CLI args that can vary freely within one job). \texttt{contention\_multigpu.sh} needs \texttt{--nodes=1}; \texttt{contention\_multinode.sh} needs \texttt{--nodes=3} -- one \texttt{\#SBATCH} header can't specify both, so they can't share a job. (\texttt{distributed} could in principle share a job with \texttt{solo}/\texttt{shared} instead, since all three only need \texttt{--nodes=1} -- not done, to keep each script's GPU request proportionate to what that specific test needs, and to avoid needing \texttt{CUDA\_VISIBLE\_DEVICES} tricks to fake "shared" behavior inside a job that actually holds 3 GPUs.)
\item \textbf{Running \texttt{contention\_multigpu.sh} and \texttt{contention\_multinode.sh} together.} Both append to the same \texttt{contention\_sweep.csv} via a non-atomic "create header if missing" check -- safe run one after another (e.g. \texttt{sbatch} one, wait, \texttt{sbatch} the other, or chain with \texttt{sbatch --dependency=afterany:<jobid>}), but a real race exists if both were ever started at the exact same instant (second header write could truncate the first script's already-appended rows). Not fixed with a lock at this point since both are run sequentially in practice.
\item \textbf{Parallelizing \texttt{format\_ppm\_ascii} with OpenMP.} Currently single-threaded, O($M^2$) work (byte$\to$ASCII digit conversion + buffer build). Not trivially parallel because output is variable-width (1--3 digits/number), so pixel $N$'s buffer offset depends on every prior pixel's digit count -- a real sequential dependency. Two ways around it: (a) a prefix-sum pass to compute per-thread offsets first, then parallel write; (b) simpler -- pad every number to fixed width (e.g. always 3 digits), making offsets trivial (\texttt{index} $\times$ \texttt{constant}), fully parallel with no coordination. Standard ASCII PPM readers tolerate zero-padded integers. \textbf{Status: measurement added, not the parallelization itself.} \texttt{cuda\_write\_ppm} now takes an optional \texttt{CudaFrameTiming*} and reports h2d/kernel/d2h/format/write time separately (via \texttt{clock\_gettime}); \texttt{run\_scenario} accumulates these and prints a per-rank "phase breakdown" line (deliberately not prefixed \texttt{"Rank "}, so \texttt{sweep\_assignment3.sh}'s parser ignores it rather than mis-parsing it into a CSV row). One added cost: an explicit \texttt{cudaDeviceSynchronize()} was reintroduced between the kernel launch and the D2H copy -- needed so \texttt{kernel\_s} and \texttt{d2h\_s} measure two separate things instead of one blurred together; not needed for correctness (the D2H copy already implicitly synced before), only for this measurement. Decision on whether to actually parallelize the ASCII formatting is deferred until these numbers are seen.
\item \textbf{Blocking \texttt{cudaMemcpy} calls.} Not an OpenMP issue, but a real blocking point: both H2D and D2H copies in \texttt{cuda\_write\_ppm} are synchronous, so the CPU sits idle waiting for the GPU during both. This is the same async/streams optimization flagged earlier as deliberately deferred (overlap frame $N$'s GPU work with frame $N{+}1$'s \texttt{compute\_next}) -- still on the table, not yet attempted (measure-first philosophy: wanted a working baseline and Nsight Systems evidence before adding this complexity).
\item \textbf{Multiple GPUs per node (\texttt{--gres=gpu:3}).} \texttt{cuda\_colorizer\_select\_device(rank)} already computes \texttt{rank \% device\_count} -- written to spread ranks across multiple GPUs automatically. All 3 ranks currently share one GPU purely because \texttt{--gres=gpu:1} makes \texttt{device\_count=1} for every rank (\texttt{rank \% 1 = 0} always), not because of a code limitation. Since each \texttt{edu\_a40} node has 4 physical A40s, \texttt{--gres=gpu:3} (still \texttt{--nodes=1}) should be enough on its own -- no code change needed -- for each rank to land on its own physical GPU. Cheaper than the multi-node option (3 GPUs on 1 node vs. 3 GPUs across 3 nodes) and exercises code that's already there. \textbf{Status: \texttt{contention\_multigpu.sh} added} (\texttt{--gres=gpu:3}), appends a \texttt{distributed} mode to \texttt{contention\_sweep.csv}; not yet run.
\end{itemize}

\subsection{Errors hit and fixes}
\begin{itemize}
\item \textbf{\texttt{nvcc fatal: Unknown option '-Wl,-rpath'}} -- caused by piping \texttt{mpicc --showme:link} output into \texttt{nvcc}; \texttt{nvcc} doesn't parse \texttt{gcc}-style linker passthrough flags the same way. Fix: \texttt{mpicc} does all MPI-aware compiling/linking itself; \texttt{nvcc} never sees an MPI flag.
\item \textbf{Nsight Compute: "option is ambiguous, matches `app-replay-buffer', \ldots"} -- caused by using \texttt{nsys}'s \texttt{-{}-} separator convention with \texttt{ncu}, which doesn't use it; the stray \texttt{-{}-} parsed as an empty-string option, ambiguous against every long option. Fix: pass the target executable directly, no separator.
\item \textbf{Nsight Compute: \texttt{ERR\_NVGPUCTRPERM}} -- GPU performance-counter access is admin-only on this cluster. Not fixable from a student account. Dropped \texttt{ncu} from the workflow entirely; relying on \texttt{nsys} + the program's own internal timers instead.
\item \textbf{Silent CSV column misalignment} -- \texttt{thread\_sweep.csv} / \texttt{blocksize\_sweep.csv} headers had one fewer column name than actual fields per row. \texttt{pandas} doesn't error on this -- it silently shifts every column name over by one (first field becomes an invisible index). Caught by manually inspecting the parsed DataFrame, not by any error message. Fixed the header lines; underlying data was fine.
\item \textbf{\texttt{edu\_a40} core count} -- hpcpolito\_guide lists 48 cores; confirmed via \texttt{sinfo -p edu\_a40 -N -o "\%N \%c \%X \%Y \%Z"} that it's actually 96 logical (2 sockets $\times$ 24 cores $\times$ 2 threads/core, SMT) -- same pattern as \texttt{edu\_sapphire} (48 listed, 96 real). Guide's number is physical cores only.
\item \textbf{Queueing got harder after the fix above} -- old \texttt{--cpus-per-task=16} only needed \texttt{3$\times$16=48} of a real 96-thread node (half), so it could schedule alongside another job using the other half. New \texttt{--cpus-per-task=32} needs the full \texttt{3$\times$32=96}, i.e. an entire idle node. Checked via \texttt{sinfo -p edu\_a40 -N -o "\%N \%C"}: at time of checking, all 4 \texttt{edu\_a40} nodes had $<$96 idle CPUs (\texttt{96/0}, \texttt{96/0}, \texttt{38/58}, \texttt{48/48} alloc/idle) -- job correctly queued (\texttt{PD}, reason \texttt{Resources}), not stuck/broken; \texttt{sbatch} would have rejected the submission outright if the request were structurally unsatisfiable, so \texttt{PD} here just means "wait for a node to fully drain."
\end{itemize}

\subsection{Results: phase breakdown (h2d / kernel / d2h / format / write)}
First run with the \texttt{CudaFrameTiming} instrumentation actually active (job 1936206, full sweep incl.\ contention; job 1936207, distributed). Decisive result:

    \caption{colorize+write split into its 5 phases vs.\ grid size. Left: full stack, absolute time -- write's dominance is the point, deliberately not log-scaled. Right: same data with write excluded, zoomed in so the shape of the other 4 phases is actually visible.}
    \label{fig:phase_breakdown}
\end{figure}
(Data note: \texttt{sweep\_assignment3.sh}/\texttt{contention\_multigpu.sh}/\texttt{contention\_multinode.sh} were updated to capture h2d/kernel/d2h/format/write into the CSVs going forward -- for this particular run, that CSV-side capture didn't exist yet at run time, so these numbers/plot were reconstructed directly from the already-completed jobs' raw text logs, which already contained every phase-breakdown line -- same real data, just re-parsed rather than requiring a cluster rerun. Script: local, one-off, not part of the checked-in pipeline.)
\begin{itemize}
\item At $M=4096$ (avg.\ over 3 ranks, totals over 50 frames): of \texttt{color\_time} $\approx$76.5s -- \texttt{write} (the \texttt{fwrite} call) $\approx$72.4s (\textbf{94.6\%}), \texttt{format} (ASCII conversion) $\approx$3.3s (\textbf{4.3\%}), \texttt{h2d}+\texttt{kernel}+\texttt{d2h} combined $\approx$0.8s ($\sim$1\%). Same lopsided pattern at every grid size swept, not just $M=4096$.
\item \textbf{Decision: do not parallelize \texttt{format\_ppm\_ascii}.} Even a theoretically perfect, zero-overhead parallelization of the ASCII-formatting step (the fixed-width-padding or prefix-sum approaches discussed earlier) would save at most $\sim$4\% of \texttt{color\_time}. Not worth the added complexity. The real cost is the disk write itself, not the formatting before it.
\item \textbf{New optimization target, if pursued further: the \texttt{fwrite} call.} At $M=4096$, \texttt{ascii\_buffer} content is roughly 100-130MB/frame; $\sim$72s/50 frames $\approx$1.44s/frame implies $\sim$70-90MB/s effective write throughput -- well below what NVMe-backed storage should sustain. Hypothesis, not yet tested: glibc's default stdio buffer for the output stream is far smaller (often 4-8KB \texttt{BUFSIZ}) than our $\sim$100MB write, so a single \texttt{fwrite()} call may still be getting split into thousands of small internal \texttt{write()} syscalls, each with kernel-transition overhead -- i.e. the earlier "batch into one buffer, one \texttt{fwrite}" optimization may not have actually produced one big write at the OS level. Worth checking with \texttt{setvbuf} (a large explicit buffer) or bypassing stdio for a raw \texttt{write()}/\texttt{pwrite()} of the whole buffer, \emph{if} a report round wants to chase this further -- not yet attempted.
\item \textbf{Measurement caveat:} a few rows show an anomalously large \texttt{kernel} time (e.g. 0.313s vs.\ a typical $\sim$0.005s) for whichever rank happens to launch its very first kernel in a run -- CUDA's one-time context/JIT warm-up cost landing on one process, not a real per-frame cost. Doesn't affect the write-dominance conclusion.
\end{itemize}

\subsection{Results: size sweep (M = 128..4096, 4 threads, --steps 50)}
\begin{itemize}
\item Plot: \texttt{plots/size\_sweep\_execution\_time.png}.
\item Execution time approaches ideal $O(M^2)$ as $M$ grows: $128\to256$ costs $2.1\times$ (fixed overhead still dominant at small $M$); $2048\to4096$ costs $4.1\times$ (essentially ideal quadratic).
\item GPU colorize+write dominates total time throughout, and the dominance is essentially constant across $M$: $\sim$98\% at $M=4096$ (79.3s / 81.1s), $\sim$98\% at $M=2048$ too. \texttt{compute\_next} stays under 2s even at $M=4096$.
\item Both phases are $O(M^2)$ $\Rightarrow$ their ratio doesn't change with $M$ -- confirmed by the above.
\end{itemize}

\subsection{Results: thread sweep (M = 4096 fixed, 1--16 threads, --steps 50)}
\begin{itemize}
\item Plot: \texttt{plots/thread\_sweep\_speedup\_efficiency.png}.
\item Both full-pipeline and compute-only speedup are essentially flat, $\leq 1.2\times$ even at 16 threads.
\item First attempt used $M=1024$ and showed the same flatness -- ruled out "not enough absolute work" as the explanation by rerunning at $M=4096$; flatness persisted, confirming it's the phase-ratio argument above, not workload size.
\item \texttt{compute\_next} time alone (isolating it from the GPU path): real but small speedup, saturates at $\sim$1.15--1.2$\times$ by 2 threads, flat through 16. Consistent with the 5-point stencil being memory-bandwidth-bound (4 loads + 1 store, few FLOPs per point) rather than compute-bound -- a couple of threads saturate available memory bandwidth.
\item Contrast with part 1: part 1 showed real OpenMP scaling at large thread counts, but tested $M$ up to 15000 -- large enough that the compute workload is interesting in isolation, no competing GPU-bound stage.
\item Pending rerun at up to 32 threads now that \texttt{edu\_a40}'s real (96-logical-core) capacity is known -- see queueing note above. Expectation: plateau continues unchanged past 16.
\end{itemize}

\begin{itemize}
\item All modes compare sim1's workload at identical parameters ($M=2048$, --steps 50, 4 threads).

\item \textbf{Finding 1 (revised) -- \texttt{distributed} barely beats \texttt{shared} this time: only $\sim$1.6\%}, essentially noise-level -- a much smaller gap than an earlier cross-run comparison suggested ($\sim$6.8\%, comparing runs from different times/cluster loads, less reliable than this internally-consistent trio). Dedicating a GPU per rank alone is not doing much here.
\item \textbf{Finding 2 -- \texttt{solo} is dramatically faster: $\sim$56\% less time than \texttt{shared}}, and $\sim$56\% faster than \texttt{distributed} too. This is the real story, and the phase breakdown (previous section) explains it: \texttt{write} (\texttt{fwrite} to disk) is $\sim$95\% of \texttt{color\_time}, and disk/filesystem write bandwidth is a resource shared by \emph{all concurrently-running processes on the node}, regardless of how many GPUs they each have. \texttt{shared} and \texttt{distributed} both have 3 ranks writing frames \emph{concurrently}; \texttt{solo} is the only mode with exactly one writer at a time. This reframes the whole contention question: \textbf{the dominant contention in this workload is concurrent disk I/O, not GPU compute-engine time-slicing} -- giving each rank its own GPU (\texttt{distributed}) does almost nothing about that, which is exactly the $\sim$1.6\% we measured.
\item \texttt{multinode}: an earlier run (job 1935733, elapsed avg 16.62s / color avg 16.20s) suggested a further improvement over \texttt{distributed}, consistent with spreading concurrent writes across separate nodes' I/O paths -- but that run predates the phase-breakdown instrumentation and was from a different job/time than the trio above, so it's not directly comparable. A fresh \texttt{multinode} run (job 1936208) is queued (\texttt{--dependency} chain behind 1936206, 1936207) to get a like-for-like number with phase breakdown; \textbf{pending} as of this writing.
\item compute\_time stays $\approx$0.41--0.44s across \texttt{solo}/\texttt{shared}/\texttt{distributed} (noise-level differences) -- correctly insensitive to GPU/node allocation, since it's pure CPU work with no GPU or cross-rank dependency. Good internal-consistency check on the measurement itself.
\item \textbf{Resolved:} the earlier caveat about missing phase-breakdown instrumentation (jobs 1935732/1935733 predating the cluster source re-upload) no longer applies to \texttt{solo}/\texttt{shared}/\texttt{distributed} above -- jobs 1936206/1936207 have full h2d/kernel/d2h/format/write data, which is what let Finding 2 above actually be explained rather than just observed. Still applies to the old \texttt{multinode} number (1935733) referenced above, and will be resolved once 1936208 finishes.
\end{itemize}
