\subsection{Introduction}
Following the initial wave simulator developed with OpenMP, this second assignment extends the application to execute multiple concurrent simulations on an HPC system using a hybrid MPI and OpenMP programming model, studying multi-wave interaction and interference dynamics under different physical conditions. OpenMP continues to handle data parallelism within each simulation, accelerating the 2D stencil computations across local CPU cores; MPI is introduced on top of it to manage task parallelism, running three distinct scenarios simultaneously as three independent ranks: Rank 0 reproduces the baseline single-wave case from Assignment 1; Rank 1 starts two impulses at once at different locations, to study wave superposition and interference; and Rank 2 delays its second impulse to a later time $t_{start}$, studying time-shifted interference instead. Since each rank advances its own simulation through the full iterative loop without ever needing to exchange data with the other two, this decoupling lets the hybrid architecture maximize computational throughput.

\subsection{Implementation}

Building upon the code developed in Assignment 1, the implementation extends the simulator to handle multiple concurrent runs. The core numerical scheme used to advance the wave field at each iteration, together with the mapping function converting field values into grayscale images (\textbf{write\_matrix}), remain identical to the first version, ensuring consistency in wave physics and visualization.

The execution starts by initializing MPI and identifying each process's rank with \textbf{MPI\_Comm\_rank}, requiring at least 3 processes to run the three required simulations simultaneously. Task parallelism is managed through conditional branching based on the process rank, where each rank specifies its scenario parameters before calling a dedicated \textbf{run\_simulation} function that encapsulates the core iterative loop advancing the simulation in time.

While data parallelism within each process is handled by OpenMP, the execution also incorporates rank-specific logic and thread-synchronization constructs for the handful of operations that must run on a single thread -- discussed in detail in the next section.

\subsection{Optimizations}
\label{sec:giro_optimizations}

Two main optimizations were applied to the algorithm on C. The first is about memory management: each MPI process independently allocates its local grid arrays (\textbf{u\_past}, \textbf{u}, and \textbf{u\_fut}) through a custom \textbf{matrix\_alloc} function that guarantees contiguous memory. Even though the three ranks are fully decoupled and never communicate, contiguous allocation remains essential for the local OpenMP threads, as it maximizes spatial locality and hardware prefetching efficiency during the 2D stencil computations, mitigating the RAM contention generated by three concurrent processes running side by side.

The second optimization tries to solve the problem of thread synchronization. Operations that must be executed by a single thread, like pointer swapping, frame saving, and the injection of the time-delayed impulse for Simulation 3, require a \textbf{pragma omp single} construct. To minimize its cost, the condition \textbf{if (rank == 2 \&\& t == n\_start)} was placed \textit{outside} the \textbf{pragma omp single} block rather than inside it. As a result, the synchronization barrier is only reached by the threads of Rank 2 at the exact time step in which the impulse must be injected; during every other iteration, and for the other two ranks at all times, the threads bypass the barrier entirely, avoiding unnecessary stalls of the whole thread team.

\subsection{The I/O bottleneck}
\label{sec:giro_io}

With these optimizations in place, the three ranks were profiled with 8 OpenMP threads each, using the edu\_sapphire partition as in Assignment 1. Execution times in \ref{fig:graph_1}, showed no significant variation between ranks, confirming a balanced workload despite their different initial conditions and branching logic. However, when compared against the Assignment 1 baseline, a severe performance degradation appeared as the matrix size $M$ increased.

This slowdown could not be attributed to the computational cost of the hybrid setup itself. Instead, it was caused by an Input/Output bottleneck: all three MPI processes attempt to format and write \textbf{.pgm} frames to the shared filesystem simultaneously, generating heavy hardware contention that stalls the CPU threads and inflates the overall execution time \cite{sanchez_cache}. To isolate the purely computational performance of the architecture, we have disabled the operation of writing to disk, and the profiling campaign was repeated while varying $M$ with 8 OpenMP threads per MPI task.

\subsection{Isolating compute: single-socket profiling}
\label{sec:giro_singlesocket}

In a first configuration, all three ranks, 24 threads in total, were confined to a single CPU socket of edu\_sapphire, without strict thread pinning, in order to evaluate the shared-memory behavior among the processes. For each rank, both a hotspots and a threading analysis were collected independently using Intel VTune Profiler.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.52\textwidth]{../Giro_part/Esercizio_2/Grafici/combo_bars_lines_1socket.png}
    \caption{Execution time and effective CPU utilization with 24 threads in one socket, swapping the M.}
    \label{fig:graph_single_socket}
\end{figure}

As shown in Figure~\ref{fig:graph_single_socket}, removing the I/O bottleneck alone produces a drastic reduction in execution time, from over 700 seconds down to approximately 61 seconds for $M = 10000$. However, Intel VTune profiling revealed a significant hardware-level anomaly: the effective CPU utilization is highly asymmetric across ranks, with Rank 1 showing a markedly lower efficiency than Rank 0 and Rank 2, even though all three processes perform the exact same amount of computation. At this point the cause of Rank 1's lower recorded utilization is not yet clear; the next experiment, designed to control socket placement explicitly, provides the answer.

\subsection{Splitting ranks across sockets}
\label{sec:giro_socketsplit}

To investigate this anomaly further, on a topology where socket boundaries could be controlled more explicitly, a second experiment was conducted on the \textbf{edu\_skylake} partition, whose nodes expose two physical sockets of 16 cores each. Three tasks of 8 threads each were requested via \textbf{--ntasks=3}, without explicit process binding, relying on OpenMPI's default placement policy. Since each socket can host at most 16 threads, the expectation was that the three ranks would naturally split across the two sockets in a 2-and-1 arrangement rather than being packed together. The profiling results confirm this: Rank 0 and Rank 2 ended up sharing the same socket, while Rank 1 was cyclically placed alone on the second socket.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.52\textwidth]{../Giro_part/Esercizio_2/Grafici/combo_bars_lines_2socket.png}
    \caption{Execution time and effective CPU utilization with Rank 1 isolated on a separate socket of edu\_skylake partition, swapping M.}
    \label{fig:graph_isolated_socket}
\end{figure}

The results in Figure~\ref{fig:graph_isolated_socket} show a clear effect of socket-level memory contention: with Rank 0 and Rank 2 sharing 16 physical cores on one socket and Rank 1 alone on the other socket, Rank 1 completed its stencil computations markedly faster than the other two, like 88 seconds versus 150 seconds at $M = 15000$.

This same test also reproduces, on a different hardware topology, the effective CPU utilization drop observed for the faster rank: because \textbf{MPI\_Finalize} is a global synchronization point, Rank 1 finishes its computation early and then idles in a spin-wait state until Ranks 0 and 2 complete. Since VTune averages effective CPU utilization over the entire process lifetime, this prolonged idle period drags down Rank 1's recorded efficiency, even though it is the fastest of the three ranks to finish. This same mechanism -- whichever rank finishes first idling at the collective barrier while VTune keeps averaging its utilization over the full run -- is the more likely explanation for the single-socket experiment's Rank 1 anomaly as well.

\subsection{Full node isolation}
\label{sec:giro_nodeisolation}

To further isolate the effect of memory locality identified in the previous experiment, a final test was conducted by running only Simulation 2 and Simulation 3 concurrently, each assigned to an entirely separate physical node on edu\_sapphire; Simulation 1 was excluded, since it reproduces the same single-wave experiment already characterized in Assignment 1. As this test was launched as an independent two-process MPI job, the ranks were renumbered accordingly, so Rank 0 and Rank 1 in the figure below correspond to Simulation 2 and Simulation 3 respectively. 
Unlike the previous setup, where isolation was achieved at the socket level within a single shared node, this configuration grants each rank exclusive access not only to its own socket, but to the entire node's memory subsystem, with no possibility of interference from the other rank. The number of OpenMP threads per rank was varied from 1 to 48 to additionally assess parallel scalability under this fully isolated condition.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.55\textwidth]{../Giro_part/Esercizio_2/Grafici/combo_bars_lines_2nodes_threads.png}
    \caption{Execution time and effective CPU utilization with Rank 0 and Rank 1 on separate physical nodes, sweep the number of threads. The two diamond markers at 8 threads report the execution times measured in the previous experiments under partial isolation, for direct comparison.}
    \label{fig:graph_two_nodes}
\end{figure}

As shown in Figure~\ref{fig:graph_two_nodes}, this configuration produces a further reduction in execution time at 8 threads compared to the previous experiments: execution time drops from approximately 150 seconds per process, measured when three ranks shared the same socket, and approximately 88 seconds, measured when one rank was isolated on a separate socket within the same node, down to roughly 57 seconds (58.9s for Rank 0, 55.9s for Rank 1) when each rank is granted an entire dedicated node. 

A second, equally important observation is that Rank 0 and Rank 1 now exhibit virtually identical execution times and effective CPU utilization at every thread count, in sharp contrast to the asymmetry observed in the single-node, two-socket experiment. Since neither rank finishes significantly ahead of the other, neither is forced into a prolonged idle spin-wait on \textbf{MPI\_Finalize}, and the CPU utilization metric is no longer artificially diluted for the faster process, indirectly confirming that the asymmetry seen earlier was indeed caused by unequal waiting time rather than unequal computational work.

Finally, effective CPU utilization increases steadily with the thread count, from about 1\% at a single thread to approximately 48\% at 48 threads, reflecting the growing fraction of the node's 96 logical cores actively engaged in computation. The best configuration observed across this campaign is therefore $M = 15000$ with 48 OpenMP threads per rank and one dedicated physical node per rank, which minimizes execution time to approximately 29 seconds, while making full use of the node's 48 physical cores without contending for shared memory bandwidth.
